## Q1. Does a recursive watch follow symlinks?

**ANSWER: It depends on platform and config. On Linux, with the default `notify::Config` (`follow_symlinks: true`), a recursive watch follows symlinks to directories, including ones pointing OUTSIDE the root, so out-of-root changes leak in. On macOS (FSEvents) it never follows symlinks and events always carry the real path. On Linux, `Config::with_follow_symlinks(false)` restores the PRD behaviour. PRD 8.1 is only true as written if we set that option.**

Default follows symlinks: `$REG/notify-9.0.0/src/config.rs:271` (`follow_symlinks: true`) (read). The inotify walk descends into symlinks when `follow_links` is set: `$REG/notify-9.0.0/src/inotify.rs:1646` (read).
The debouncer can pass a notify config: `notify-debouncer-mini-0.8.0/src/lib.rs:172` `with_notify_config` (read). I applied `with_follow_symlinks(false)` through the raw watcher only (the debouncer wraps the same watcher; not run through the debouncer, so that last link is read, not measured).

| What I did | What I saw | Platform |
|---|---|---|
| Recursive watch, default config. Layout: `root/docs/a.md`, `root/inlink -> root/docs` (in-root dir link), `root/outlink -> ../outside` (out-of-root dir link). Modify `docs/a.md` (real path) | `DEB Any docs/a.md` (1720 ms) | macOS (measured) |
| same, modify `inlink/a.md` (link path) | `DEB Any docs/a.md`, i.e. reported under the REAL path, not `inlink/a.md` | macOS (measured) |
| same, modify `outside/o.md` and `outlink/o.md` | no event at all for either | macOS (measured) |
| same, create `outlink/new.md` | no event; create `inlink/new.md` gives `DEB Any docs/new.md` | macOS (measured) |
| Same layout, modify `docs/a.md` (real path) | `DEB Any root/inlink/a.md` (link path!) | Linux, follow=true (measured) |
| same, modify `inlink/a.md` | `DEB Any inlink/a.md` | Linux, follow=true (measured) |
| same, modify `outside/o.md` (a file OUTSIDE the root) | `DEB Any outlink/o.md` | Linux, follow=true (measured) |
| same, modify `outlink/o.md`, create `outlink/new.md` | `DEB Any outlink/o.md`, `DEB Any outlink/new.md` | Linux, follow=true (measured) |
| Repeat with link named `aaa-link` and `zzz-link` (name sorts before/after `docs`) | real-path write is reported as `aaa-link/a.md` / `zzz-link/a.md` in both cases. The link path wins (aliased inotify descriptor is reported under one path; `inotify.rs:250-256`, `:1486-1510` read) | Linux, follow=true (measured) |
| `Config::with_follow_symlinks(false)`, writes via `docs/a.md`, `inlink/a.md`, `outside/o.md`, `outlink/o.md` | `docs/a.md` and `inlink/a.md` both reported as `docs/a.md`; `outside/o.md` and `outlink/o.md` produce no events | Linux (measured) |
| same config | same result as default (real path only, no out-of-root events) | macOS (measured; option has no visible effect on FSEvents) |

Consequences: (1) Linux default would deliver events for files outside the root, so a watcher we expect to be sandboxed is not. Our code would also receive paths with an `outlink/` prefix that look in-root. (2) With follow=false, in-root link targets are covered by the single recursive watch and are reported under the real path on both platforms, which is exactly what the PRD alias map (8.2) expects. Never rely on the link path appearing in an event.

## Q2. Can ignored directories be excluded from watching?

**ANSWER: Not with a recursive watch. `notify` has no ignore/exclude option, and a recursive watch registers OS watches for every directory under the root, ignored ones included. On Linux that is a real cost (208 inotify watches versus 3 in my test tree); on macOS FSEvents reports events from ignored dirs but has no per-directory watch cost. Option (b) (non-recursive watch per visible directory) does exclude them on both platforms, but a directory created later is not watched automatically and must be added by our code.**

No exclude/ignore setting exists in `notify` config: grep for `exclude|ignore` in `$REG/notify-9.0.0/src/config.rs` and `lib.rs` found nothing (read; `grep` for those files printed nothing, only the path warning). Test tree: `src/`, `docs/`, `.git/` (+`objects`), `node_modules/` with 102 subdirs, 100 of them with a `lib/` child.

| What I did | What I saw | Platform |
|---|---|---|
| (a) one recursive watch, count `inotify wd:` lines in `/proc/<pid>/fdinfo` | **208 watches** registered (includes ignored dirs) | Linux (measured) |
| (b) 3 non-recursive watches (`root`, `src`, `docs`; walk skipped `.git`, `node_modules`) | **3 watches** | Linux (measured) |
| (a) write `node_modules/pkg/f.js`, `.git/HEAD` | events arrive: `Modify(Data(Any)) node_modules/pkg/f.js`, `.git/HEAD` (so our code must filter) | Linux (measured) |
| (a) same writes | events arrive: `Modify(Data(Content)) node_modules/pkg/f.js`, `.git/HEAD` | macOS (measured) |
| (b) same writes | no events for `node_modules` or `.git`; `src/a.md` write arrives | Linux and macOS (measured) |
| (a) `mkdir src/newdir`, then write `src/newdir/n.md` | `Create(Folder)` then `Create(File) src/newdir/n.md`, further writes reported | Linux and macOS (measured) |
| (b) same | `Create(Folder) src/newdir` arrives, but writes inside `newdir/n.md` produce NO events (dir not watched) | Linux and macOS (measured) |
| Per-directory registration count on macOS | not measured (FSEvents is a stream per path, no `/proc` equivalent used) | macOS |

Trade-off: (a) is simpler and correct for new directories, but on Linux a repo with big `node_modules`/`target` trees burns watch budget and can hit the limit (Q5) because of directories we will never show. (b) is frugal but needs add-watch logic on `Create(Folder)` and has a race window between mkdir and the new watch (files written in that window are missed; the PRD rescan on directory creation would cover it).

## Q3. Can removal be distinguished from change with `notify-debouncer-mini`?

**ANSWER: No. The debouncer emits only `DebouncedEventKind::Any` or `AnyContinuous` plus a path. There is no create/modify/remove/rename kind and no file-vs-directory information. Removal must be detected by checking the disk and the snapshot, which is what PRD 8.2 already does.**

Types: `DebouncedEventKind { Any, AnyContinuous }` with the doc "Does not emit any specific event type on purpose" (`$REG/notify-types-2.3.1/src/debouncer_mini.rs:10-14`, doc comment above `DebouncedEvent`) (read). `debounced_events()` only ever builds those two kinds (`notify-debouncer-mini-0.8.0/src/lib.rs:282-310`) (read). `add_event` keeps only `event.paths`, discarding the event kind (`lib.rs:~340`, read).

Debouncer output (200 ms window, one op at a time, 0.8 s apart; raw kind shown for comparison):

| Operation | Debouncer output | Raw notify kinds (macOS) | Raw notify kinds (Linux) |
|---|---|---|---|
| modify `mod.md` | `Any mod.md` | `Modify(Data(Content))` | `Modify(Data(Any))`, `Access(Close(Write))` |
| delete `del.md` | `Any del.md` | `Remove(File)` | `Remove(File)` |
| create `new.md` | `Any new.md` | `Create(File)`, `Modify(Metadata(Extended))`, `Modify(Data(Content))` | `Create(File)`, `Modify(Data(Any))`, `Access(Close(Write))` |
| rename `old.md` to `renamed.md` | two events: `Any old.md`, `Any renamed.md` (order is not stable: mac run gave renamed first, Linux run old first; the debouncer keeps paths in a `HashMap`, read `lib.rs:~282`) | `Modify(Name(Any))` for each path | `Modify(Name(From))`, `Modify(Name(To))`, `Modify(Name(Both))` with both paths |
| mkdir `sub` | `Any sub` | `Create(Folder)`, `Modify(Metadata(Extended))` | `Create(Folder)` |
| rmdir `sub` | `Any sub` (identical to mkdir) | `Create(Folder)`, `Modify(Metadata(Extended))`, `Remove(Folder)` (stale Create flag replayed on mac) | `Remove(Folder)` |
| mkdir `sub2`+file, `rm -r` 100 ms later | `AnyContinuous sub2`, `AnyContinuous sub2/f.md`, then `Any sub2`, `Any sub2/f.md` | creates and removes mixed | `Create`, `Remove(File)`, `Remove(Folder)` |
| create then delete `tmp.md` inside one window | `Any tmp.md` (path still reported though the file is already gone) | `Create`..`Remove(File)` | same |
| atomic save: write `.mod.tmp`, rename over `mod.md` | `Any .mod.tmp`, `Any mod.md` | | |

All rows are measured; full dumps in `mac-q3.txt` and `linux-q3.txt` under the scratch dir. Observations that matter to the design:
- macOS FSEvents coalesces flags per path: a plain modify can surface as `Create(File)` plus `Modify(Metadata)` plus `Modify(Data)`, and an rmdir replays `Create(Folder)` (measured). Even the raw kind is not a reliable change-vs-remove signal on macOS.
- `AnyContinuous` is emitted when a path has been active for at least the window, and the final `Any` follows later (`lib.rs:282-310` read; seen in the `sub2` row). Treat both kinds as "this path was touched".
- Paths created and removed inside one window still arrive (`tmp.md`), so the classification table's "no in snapshot, missing on disk gives ignored" row is necessary.
- A directory event cannot be told from a file event in the debouncer output (`sub` is just `Any sub`).
- Plain reads (`cat`, `ls`, `stat`) produced no debouncer events on either platform (measured, `mac-q6.txt`, `linux-q6.txt`), so the server reading files does not self-trigger reloads. Raw Linux events do include `Access(Open)`/`Access(Close)`; the debouncer path did not surface them in these runs.

## Q4. What do overflow and lost events look like in the API?

**ANSWER: `notify-debouncer-mini` 0.8.0 exposes a dedicated `DebouncedEventBatch::Rescan` variant, delivered immediately (not debounced) and applying to the whole watcher; the handler type is `Result<DebouncedEventBatch, notify::Error>`. Raw `notify` exposes it as an event with `EventKind::Other` and `Flag::Rescan` (`event.need_rescan()`). I reproduced both: on Linux by lowering `max_queued_events`, on macOS by a 30,000 file burst.**

Source (read): handler result `pub type DebounceEventResult = Result<DebouncedEventBatch, Error>` (`notify-debouncer-mini-0.8.0/src/lib.rs:243`); rescan branch `Ok(InnerEvent::NotifyEvent(Ok(event))) if event.need_rescan() => handler(Ok(DebouncedEventBatch::Rescan))` (`lib.rs:~392-394`); variant defined at `notify-types-2.3.1/src/debouncer_mini.rs:43-52` (`#[non_exhaustive]`, so match arms need a wildcard). Doc says it "applies to all watched paths", "delivered without waiting for the debounce timeout", pending paths keep their normal deadlines (`lib.rs:72-75`).
Backends: inotify `Q_OVERFLOW` becomes `Event::new(EventKind::Other).set_flag(Flag::Rescan)` (`notify-9.0.0/src/inotify.rs:590-592`); FSEvents `MustScanSubDirs` becomes the same, with `info` = `"rescan: user dropped"` or `"rescan: kernel dropped"` (`fsevent.rs:25-27`, `:270-271`). `Event::need_rescan` at `notify-types-2.3.1/src/event.rs:737`.

| What I did | What I saw | Platform |
|---|---|---|
| 5,000 files created in a tight loop with `/proc/sys/fs/inotify/max_queued_events` lowered from 1048576 to 16 (restored after) | raw: `RAW RESCAN Event { kind: Other, paths: [], attr:flag: Some(Rescan) ... }`; debouncer: `DEB BATCH Rescan` (twice), then the path events | Linux (measured) |
| 30,000 files with the default queue (1048576) | no Rescan, 120,003 raw events | Linux (measured) |
| 30,000 files created in a tight loop, default settings, debug build | raw: 88 `RESCAN` events, first at 280 ms with `paths: ["<root>"]`, `info: Some("rescan: user dropped")`; debouncer: 4 `DEB BATCH Rescan` (an earlier run saw 12); counts vary per run | macOS (measured) |

Note: on Linux real overflow needs a queue that fills faster than the consumer drains. With the default 1M queue I could not provoke it; the lowered limit is an artificial reproduction of the same kernel signal. Besides `Rescan`, `Err(notify::Error)` can arrive on the same channel for backend failures; the only concrete variant I exercised is `MaxFilesWatch` (Q5).

## Q5. What does the inotify watch-limit failure look like?

**ANSWER: `watch()` returns `Err(notify::Error)` synchronously with `kind() == notify::ErrorKind::MaxFilesWatch` (display: `OS file watch limit reached.`), with the failing directory in `paths`. It is raised when `inotify_add_watch` returns `ENOSPC`. The limit is `fs.inotify.max_user_watches`, counted per user across all processes. A recursive watch that runs out partway returns the error, with only the directories registered before the failure watched. Reproduced.**

Source (read): `ENOSPC` maps to `Error::new(ErrorKind::MaxFilesWatch)` at `notify-9.0.0/src/inotify.rs:1251-1253` (comment: "do not report inotify limits as no more space"); message text at `notify-9.0.0/src/error.rs:164`; variant at `error.rs:37`.

Reproduction: container with `--privileged` so `/proc/sys` was writable (the inotify sysctls are not private to the container, so I restored the original value after each run; `1048576` restored, confirmed). Tree: 301 directories (`root/d1..d300`). `max_user_watches` was swept.

| What I did | What I saw | Platform |
|---|---|---|
| limit 200, recursive watch (debouncer) | `WATCH ERR ... Error { kind: MaxFilesWatch, paths: ["root/d40"] } display: OS file watch limit reached. about ["root/d40"]`, no panic; process kept running | Linux (measured) |
| limit 300 / 400, recursive | same error, failing path `root/d140` / `root/d240` | Linux (measured) |
| limit 600 / 1000, recursive | success | Linux (measured) |
| limit 100 | error even for a single non-recursive watch on `root` (other processes of the same uid already hold watches; the limit is shared, so first failure positions shift) | Linux (measured) |
| limit 200/300/400, 301 non-recursive per-directory watches | 261/161/61 `MaxFilesWatch` errors respectively (about 40 watches were already used elsewhere) | Linux (measured) |

Caveat: error occurs at registration time. A server that ignores it keeps a half-registered watcher that silently misses changes; it should drop the watcher and report unavailable.

## Implications for the PRD

1. **8.1 first bullet needs a wording and implementation change.** "Symlinks pointing outside the root are never watched" is FALSE on Linux with the default config (measured: events for `outside/o.md` arrive as `outlink/o.md`). Required: build the debouncer with `notify::Config::default().with_follow_symlinks(false)` (via `notify_debouncer_mini::Config::with_notify_config` and `new_debouncer_opt`). Add that as a stated requirement, and add an acceptance test with an out-of-root link on Linux. The claim "in-root symlink targets are covered by the recursive watch" is confirmed on both platforms.
2. **8.1 event path mapping: add a note that event paths are real paths.** With follow=false both platforms report an in-root link target under the real path (`docs/a.md`, never `inlink/a.md`). The alias map in 8.2 is therefore mandatory, not an optimisation. With follow=true on Linux the reported path can be the link path, so the default must not be used.
3. **8.1 third bullet ("should avoid watching ignored directories") must be restated.** `notify` cannot exclude directories from a recursive watch. On Linux a recursive watch costs one inotify watch per directory including `node_modules`/`.git` (208 versus 3 measured). Pick one explicitly: (a) recursive watch plus event filtering (simple, correct for new dirs, wastes the shared inotify budget), or (b) per-directory non-recursive watches (frugal, but our code must add a watch on every `Create(Folder)` and handle the race). Suggested wording: "Ignored directories are filtered from events; the OS may still watch them (Linux inotify costs one watch per directory)", unless the owner picks (b). I recommend (a) for v1 because 8.2 already triggers a full rescan on directory creation, and documenting the watch-limit mitigation in 8.5.
4. **8.2 classification: confirmed workable, one clarification.** The table does not rely on event kinds, which is right because the debouncer has none. Add to the text: the debouncer gives no file-vs-directory flag, so "a created, deleted or renamed directory" must be detected by comparing against the previous tree snapshot and by `stat` (a removed directory is a path that was a directory in the snapshot and is now missing). A path created and removed in one window still arrives, covered by the "no / missing: ignored" row. A rename arrives as two `Any` events (old and new path), no pairing.
5. **8.2 rescan sentence: name the API.** "a `notify` rescan or overflow notice" maps to `DebouncedEventBatch::Rescan` (immediate, not debounced). Also note it is `#[non_exhaustive]` so the match needs a wildcard, and that on macOS it can arrive repeatedly in a burst (up to 88 raw / 4 debounced in one 30k-file run), so rescans should be coalesced by the "at most one rebuild at a time" rule in 8.3 (already there).
6. **8.5 failure text: confirmed, tighten.** Detect with `err.kind() == notify::ErrorKind::MaxFilesWatch`; `watch()` returns it synchronously. The recursive watch can fail partway (failure path `root/d40` in the 200 limit run), so on any error from the initial `watch()` drop the watcher entirely and send `unavailable`; do not keep the half-registered one. The reason text can be `OS file watch limit reached.` and may suggest raising `fs.inotify.max_user_watches`.
7. **Debounce default 200 ms: confirmed.** Observed 200 to 224 ms from write to delivered batch on both platforms; AC-47/AC-48 timing budgets should allow at least 300 ms for the notify-to-SSE leg.
8. **No change needed** to the pipeline order in 8.3 or the client behaviour in 8.4. Reads by the server did not trigger events (measured), so there is no self-notification loop to guard against.

## Addendum (milestone M4, 2026-11-24): the debouncer forwards our own directory reads on Linux

Q3 above says plain reads (`cat`, `ls`, `stat`) produced no debouncer events. That held for those commands, but it did **not** hold for the server's own tree scan on Linux: `read_dir` on a watched directory emits inotify access events for that directory, and `notify-debouncer-mini` 0.8.0 forwarded them as touched paths. Measured in a Linux container (`DOCS_BROWSER_TRACE` printed each batch): an idle server, with nothing touched, received batches containing only directories (`site`, `docs`, `docs/dir.md`, `docs/subdir`, `loop`), rebuilt the tree for each, and sent a `tree` event every few hundred milliseconds. Ignored directories were absent from the batches because the scanner never opens them. macOS FSEvents has no such events, so the same code was quiet on macOS.

Resolution: use raw `notify` events, drop `EventKind::Access(_)`, and debounce in the state task (quiet period 200 ms, cap 1 s). Guarded by UT-12 (`relevance()`), and by the idle-silence assertion in AC-48 and AC-57 (mutation checked on Linux: counting access events as changes makes AC-48 fail).
